# Редактирование профиля

## Пользовательский сценарий

Меню пользователя → «Профиль» или маршрут `/profile` после входа.

Страница получает сохранённый профиль и показывает одно редактируемое поле «Имя»
(`display_name`). Оно используется в меню пользователя; можно указать настоящее
имя или псевдоним. Username, никнейм, профессия и «О себе» убраны из формы:
в текущем интерфейсе у них нет отдельной пользовательской задачи.

Email показан только для чтения. В данном API нет изменения email.
Фото профиля можно загрузить, заменить и удалить. После выбора файла оно
сохраняется отдельно от имени; несохранённое имя остаётся в форме. Меню показывает
ту же фотографию, а без неё — первую букву имени.

Изменения сохраняются явно кнопкой «Сохранить», не автоматически.
«Отменить изменения» возвращает последние полученные серверные значения
без запроса на запись. Неизменённую форму отправить нельзя.
Имя необязательно: очистка удаляет только display_name. Скрытые поля не очищаются.

Сохранённый профиль относится к аккаунту, не к устройству или отдельной книге.
Черновик формы хранится только в памяти этой страницы. При переходе со страницы
без сохранения черновик теряется; предупреждение о несохранённых изменениях
пока не реализовано.

## Аватар и выход на всех устройствах

Аватар использует `PUT /api/profile/avatar` (multipart, поле `file`, ответ 204),
`GET /api/profile/avatar` (JPEG/PNG) и `DELETE /api/profile/avatar` (204).
Каждый запрос идёт через общий клиент с Bearer JWT и продлением сессии.
Прямая ссылка `<img src="/api/profile/avatar">` не используется, поскольку тег
изображения не может передать этот JWT. GET возвращает Blob; один object URL
разделяется между профилем и меню. URL освобождается при замене, удалении и
размонтировании provider, включая выход/смену аккаунта. В storage фото не пишется.

Клиент принимает непустые JPEG/PNG до 2 МиБ — это текущие ограничения по умолчанию
backend. Содержимое, разрешение (по умолчанию до 4096 × 4096), декодирование и
нормализацию проверяет сервер; клиентская проверка MIME не заменяет серверную.
При успешном 204 флаг has_avatar обновляется без изменения имени/даты.
Замена вызывает новый GET нормализованного изображения, а не показ локального
файла как якобы сохранённого. Если GET не удался, есть повторная загрузка;
404 означает отсутствие фото. При ошибке декодирования img отображается буква.
Изменение аватара и сохранение имени сериализованы одним блокиратором записи.
GET ограничен 10 секундами, PUT/DELETE — 15. Запоздалые ответы игнорируются.
Отмена ожидания не гарантирует отмену записи на сервере.

Красный текст с иконкой выхода внизу профиля открывает нативный модальный dialog.
Фокус сначала на «Отмена»; Escape и отмена не отправляют запрос.
Подтверждение вызывает существующий `logoutEverywhere` и
`POST /api/auth/logout-all`; успешный ответ отзывает сессии, удаляет локальное
состояние авторизации, синхронизирует выход с другими вкладками и ведёт на /login.
Во время запроса повторные нажатия и закрытие диалога заблокированы.
HTTP-ожидание logout-all ограничено 15 секундами. При неуспехе нет ложного
сообщения об успешном выходе: диалог показывает ошибку и допускает повтор.
401 может завершить уже недействительную локальную сессию по общей auth-логике.
Безопасный диалог использует нативный focus trap и возвращает фокус на кнопку.

## Контракт backend

- `GET /api/profile` → `ProfileResponse`.
- `PUT /api/profile` + JSON `UpdateProfileRequest` → обновлённый `ProfileResponse`.
- Оба запроса используют Bearer JWT и общий клиент с существующим обновлением сессии.
- В разработке браузер обращается к `/api`; Vite проксирует запрос в `localhost:8080`.

PUT полностью заменяет текстовые поля, поэтому frontend отправляет **все пять полей**.
Нельзя послать только новое имя: остальные отсутствующие поля backend нормализует в null.
Frontend убирает внешние пробелы только у редактируемого имени и передаёт null
при его очистке. Скрытые username, nickname, profession и bio передаются без
изменений из **последнего полученного профиля**, включая null. Даже если фоновый
GET обновил эти значения во время редактирования имени, PUT использует свежие
данные, а не снимок на момент открытия формы. Версии/ETag в API нет, поэтому
изменения на другом устройстве после последнего GET всё ещё могут быть перезаписаны.
Email, user_id, has_avatar, даты создания и изменения в запрос записи не входят.

Валидация соответствует `UpdateProfileRequest.java`:

| Поле | Правило |
| --- | --- |
| username | 3–30 символов; `^[A-Za-z][A-Za-z0-9_]{2,29}$`; пустое допустимо |
| display_name | до 80 символов |
| nickname | до 50 символов |
| profession | до 100 символов |
| bio | до 1000 символов |

Регистр username сохраняется. Username не заменяет email для входа.
Миграция V5 удаляет уникальность username; frontend не выдумывает проверку «имя занято».

Ответ записи проверяется по структуре DTO. Некорректный ответ не считается
успешным сохранением в интерфейсе. Страница также не позволяет редактировать
неполный или некорректный первоначальный профиль.

## Состояние и защита от гонок

`ProfileProvider` — единый источник сохранённого профиля для меню и страницы.
После успешного PUT он принимает возвращённый сервером объект, поэтому имя
и буква аватара в меню меняются сразу, без дополнительного GET.

Обновление access token не вызывает повторный GET и не сбрасывает форму.
Следующий запрос использует актуальный JWT.
При смене аккаунта layout/provider пересоздаётся, данные предыдущего пользователя
не сохраняются в localStorage или sessionStorage.

Загрузка ограничена 10 секундами, сохранение — 15 секундами.
Запросы отменяются при размонтировании. Номер операции и AbortSignal защищают
от запоздавшего GET, который иначе мог бы затереть только что сохранённые данные.
Перед PUT старый GET отменяется. Одновременные записи заблокированы.

Фоновое обновление чистой формы меняет её поля. Если уже есть черновик,
он не перезаписывается. Явная отмена черновика возвращает самый свежий профиль,
который известен provider.

AbortSignal отменяет ожидание ответа в браузере, но **не гарантирует откат PUT
на сервере**. Если связь пропала после записи, профиль мог сохраниться.
Поэтому сообщение говорит «Не удалось подтвердить сохранение», а не утверждает,
что сервер ничего не изменил. Автоматического повторного PUT нет.

При одновременном редактировании с разных устройств текущий backend использует
полную замену без версии/ETag: последняя принятая запись имеет приоритет.

## Ошибки и обратная связь

- Локальная ошибка: поле получает текст ошибки и фокус; PUT не отправляется.
- HTTP 400: ошибка имени отображается рядом с полем, остальные ошибки — общим уведомлением. Java-ключ `displayName`
  переводится в frontend-поле `display_name`.
- HTTP 403: сообщение об отсутствии доступа.
- HTTP 429: предложение подождать перед повторной записью.
- Ошибка сети, таймаут или некорректный ответ: черновик сохраняется в форме,
  доступно повторное ручное сохранение.
- Ошибка первоначального GET: кнопка «Загрузить снова».
- Пока идёт запись, поля и кнопки сохранения/сброса заблокированы.
- Сообщение «Профиль сохранён» исчезает через 5 секунд или при новой правке.

UI использует существующие цвета и отступы приложения, поддерживает RU/EN,
светлую/тёмную тему и одноколоночную форму на всех размерах экрана.
Полям сопоставлены label, сообщениям — aria-describedby и role alert/status.

## Структура

- `src/pages/ProfilePage.tsx` — маршрут, загрузка и ошибки.
- `src/components/profile/ProfileForm.tsx` — черновик, отправка и сброс.
- `src/components/profile/ProfileField.tsx` — отдельное поле и ошибки.
- `src/profile/profileForm.ts` — правила валидации и преобразование JSON.
- `src/profile/ProfileProvider.tsx` — сохранённый профиль, запросы и защита от гонок.
- `src/api/profile.ts` — GET/PUT профиля, JPEG/PNG Blob, multipart PUT и DELETE аватара.
- `src/profile/useProfileAvatar.ts` — общая фотография, повторы, таймауты и освобождение URL.
- `src/components/profile/ProfileAvatarEditor.tsx` — выбор/замена/удаление фотографии.
- `src/components/profile/LogoutAllSection.tsx` — подтверждение и выход везде.
- `src/components/ui/ConfirmDialog.tsx` — доступный нативный диалог подтверждения.

## Проверки

```bash
npm run lint
npm test
npm run build
# Нужны запущенный frontend и установленный Google Chrome:
npm run test:profile
npm run test:account
npm run test:viewer
```

Тесты профиля покрывают полное тело PUT, нормализацию, пустые поля, ограничения,
упрощённую форму, сохранение скрытых полей (в том числе после фонового GET),
обновление меню, ошибки, таймауты, повторные
нажатия, смену аккаунта, JWT, поздние ответы и сохранение черновика при фоновом GET.

Тесты аватара и выхода дополнительно проверяют multipart/JWT, MIME/размер,
сохранность черновика, ошибки загрузки/удаления, освобождение URL, таймауты,
повторные нажатия, смену аккаунта, отмену/фокус/ошибку подтверждения выхода.

Browser smoke работает с настоящим App и перехваченными API-ответами
в отдельном браузерном контексте. Он не изменяет настоящие профили в базе данных.
Backend-файлы не изменялись.

Дополнительно проверен реальный GET /api/profile через Vite-прокси на тестовом аккаунте:
ответ 200 соответствует DTO. Текстовые данные настоящего профиля не изменялись;
созданная для этой проверки сессия завершена с 204.
