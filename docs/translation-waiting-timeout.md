# Ограничение ожидания перевода

Frontend больше не показывает бесконечное «Переводится», когда задача не движется
или backend не отвечает. Backend и API DTO не изменялись.

## Поведение

- PENDING показывается как «Ожидает обработки», PROCESSING — «Переводится».
- Статус существующей задачи проверяется каждые 2,5 секунды.
- Отдельный GET-запрос имеет предел 10 секунд. При превышении он отменяется:
  один зависший запрос не блокирует все дальнейшие проверки.
- Если статус или прогресс не меняются 2 минуты, автоматические проверки этой
  задачи прекращаются. Изменение статуса/прогресса запускает отсчёт заново.
- У каждой книги свой отсчёт; прогресс другой книги его не сбрасывает.
- Показывается «Ожидание приостановлено». Если backend не присылал корректные
  ответы, сообщение отдельно предлагает проверить соединение.
- «Проверить статус» возобновляет GET-проверки того же job_id. POST загрузки не
  выполняется, новая задача не создаётся. Если результат уже DONE, он открывается.

Это остановка ожидания во frontend, не отмена серверного перевода. Задача
остаётся PENDING/PROCESSING и может завершиться позже. Frontend не подменяет
серверный статус на FAILED и не возвращает расходованные лимиты. Для настоящей
отмены и восстановления лимитов нужен согласованный backend endpoint.
После паузы поздний результат можно получить ручной проверкой или обновлением
истории/страницы; автоматически frontend больше не опрашивает эту задачу.

Таймаут относится к отсутствию изменений, не к общей длительности перевода:
длинная книга может обрабатываться дольше двух минут, если приходят обновления.
Если ML редко отправляет прогресс, пауза всё равно возможна; она не означает
доказанную поломку ML. По статусу задачи нельзя достоверно определить причину.

## Состояние и жизненный цикл

serverStatus содержит настоящий статус API. waitingIssue — только состояние
интерфейса: stalled либо unreachable. Оно не добавляется в backend DTO.
Пауза отражается в toolbar, панели перевода, Sidebar и истории.

Отсчёт начинается при наблюдении задачи во frontend, не по серверному created_at.
Обычные перерисовки, смена книги и обновление JWT его не сбрасывают. Повторная
загрузка истории с тем же статусом/прогрессом сохраняет паузу; новый прогресс или
DONE/FAILED очищают её. После полной перезагрузки отсчёт начинается заново.

Таймеры учитывают Date.now, поэтому после сна устройства/фоновой вкладки
следующая проверка замечает истёкший срок. Проверки периодические: отображение
паузы может произойти немного позже границы двух минут.
Запросы ограничены AbortController и Promise.race. Ответ после удаления,
приостановки, замены задачи или размонтирования не применяется.

## Проверки

10 новых тестов проверяют неизменный PENDING, зависшие GET-запросы, прогресс,
переход PROCESSING, JWT-ротацию, независимые книги, ручное возобновление,
удалённую задачу, размонтирование и некорректный job_id в ответе.
Браузерный сценарий проверяет остановку GET-запросов после таймаута и получение
готового файла для прежнего job_id без нового POST. API в этом сценарии
подставляется в изолированном Chrome; реальные backend-данные не меняются.

Ручная проверка: открыть PENDING-задачу без подключённого ML, оставить приложение
открытым две минуты. Должны появиться объяснение и «Проверить статус», а запросы
статуса прекратиться. Нажатие кнопки должно выполнить GET прежнего job_id,
без повторной отправки исходного файла.
