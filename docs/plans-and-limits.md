# Тариф и лимиты в интерфейсе

## Где находится

Раздел `/plans` доступен после входа через меню пользователя → «Тариф и лимиты».
Остаток и расход переводов показаны только в этом разделе, без отдельной карточки в боковой панели.
Редактирование профиля доступно отдельным пунктом меню. Удаление, закрепление и переименование книг не добавлены.

## Реальные данные, а не демонстрационные тарифы

Frontend использует защищённые GET-запросы:

- `/api/account/usage` — действующий тариф, использованные единицы, остаток, лимит и дата нового периода.
- `/api/account/subscription` — подписка, её статус, даты периода и признак отмены в конце периода.

Запросы используют общий клиент с Bearer JWT и существующим продлением сессии.
Адрес браузерного API — `/api`, в разработке Vite проксирует его на `localhost:8080`.

Модуль `src/api/account.ts` проверяет полученные DTO во время выполнения.
Отсутствующие или некорректные данные не превращаются в Free, нулевой остаток или безлимит.
Для безлимита сервер передаёт `unlimited: true`, `limit_units: null` и `remaining_units: null`.
Для ограниченного тарифа интерфейс использует именно `remaining_units`, не пересчитывает его по истории.
Индикатор расхода ограничен верхней границей: после изменения тарифа использованных единиц может быть больше нового лимита.

Размеры лимитов, цены и преимущества других тарифов не придуманы.
На проверенном локальном backend 9 октября 2026 года тестовый аккаунт получал Free:
`limit_units: 5`, `used_units: 2`, `remaining_units: 3`.
Это результат проверки, а не значение, зашитое в приложение.
Название тарифа отображается из `plan_display_name`; его локализацию определяет backend.

## Почему тариф и подписка показаны отдельно

`AccountUsageService` получает реально действующее право через `EntitlementService`.
Расширенные лимиты даёт только активная подписка в действующем периоде.
`AccountSubscriptionService` также может вернуть подписку со статусом `PAST_DUE`.
Поэтому Pro с задолженностью и одновременно действующие лимиты Free — допустимый ответ,
а не ошибка интерфейса. Основное название тарифа и счётчик берутся из usage.
Все статусы DTO имеют подписи: FREE, ACTIVE, PAST_DUE, CANCELED, EXPIRED.

## Когда расходуется перевод

`TranslationJobCreationService.create` резервирует одну единицу, создаёт задачу и сразу
вызывает `UsageLimitService.consume` в той же транзакции.
Расход появляется при создании задачи, до её завершения, а не только после DONE.
`sumOccupiedUnits` учитывает RESERVED и CONSUMED.

Frontend не обещает возврат единицы после FAILED: такого поведения в проверенном
обработчике завершения нет. При смене статуса он заново получает счётчик с сервера,
а не уменьшает его самостоятельно.

Период — календарный месяц по UTC. Новый период наступает в `resets_at`.
Дата отображается в местном времени браузера с учётом языка интерфейса.
Период расхода не следует путать с датами платной подписки.

## Обновление и ошибки

`AccountProvider` хранит данные только в памяти внутри layout авторизованного пользователя:

- первичная загрузка после входа;
- обновление после принятой загрузки документа;
- однократное обновление для завершившейся или ошибочной задачи;
- обновление после отказа загрузки с HTTP 429;
- ручная кнопка «Обновить данные»;
- возвращение во вкладку, не чаще одного запроса пары endpoint за 30 секунд;
- наступление даты нового периода или конца периода подписки.

Сама ротация access token не запускает лишнюю загрузку счётчиков.
Новые запросы используют актуальный токен. Смена аккаунта размонтирует provider.
При размонтировании и повторной загрузке запросы отменяются; поздний ответ игнорируется.
Таймаут — 10 секунд. Подписка и usage загружаются независимо:
ошибка одного endpoint не скрывает успешный ответ другого.

При неудачном обновлении последние данные остаются на странице с предупреждением,
что они могут быть устаревшими. Подпись тарифа в меню показывает недоступность.
Frontend не запрещает новую загрузку по потенциально устаревшему снимку usage:
окончательное решение о лимите принимает backend.

HTTP 429 может означать и квоту, и ограничение частоты. Backend пока не выдаёт отдельный
машиночитаемый код ошибки квоты. Для существующего сообщения
«Лимит использования функции на текущий период исчерпан» показывается отдельная подсказка;
остальные 429 сохраняют обычное сообщение о частоте загрузок.
Автоматической повторной отправки файла нет.

Просмотр и скачивание уже загруженных книг не блокируются из-за нулевого остатка.

## Ограничения этого этапа

Покупка, оплата, изменение и отмена подписки через UI не реализованы.
Backend endpoints для покупки и отмены существуют, но эта страница их не вызывает.
Каталог цен и сравнение тарифов пока не показаны: DTO usage описывает текущий тариф,
а не полный набор возможностей всех планов.

В карточке загрузки указаны действующие общие ограничения проекта:
PDF, DOCX, DOC и максимум 20 × 1024 × 1024 байт.
Это не преимущество Pro и не отдельный лимит Free. Backend задаёт размер через
`DOCUMENT_MAX_FILE_SIZE`, frontend уже проверяет тот же размер локально.
Если конфигурацию backend изменят, frontend-проверку и подпись нужно обновить:
текущий API не передаёт максимальный размер файла.

Заметки, их хранение и меню операций над книгой остаются вне этого этапа.
Backend не изменялся.

## Как проверить

1. Войти и открыть меню пользователя → «Тариф и лимиты».
2. Сравнить значения с GET `/api/account/usage` в Network.
3. Отправить документ: после принятого upload остаток должен обновиться.
4. Отключить сеть и обновить данные: ошибка должна быть видна, старые значения помечены.
5. Вернуть сеть и повторить обновление.
6. Проверить светлую/тёмную тему, RU/EN и доступность меню на узком экране.

Автоматические проверки:

```bash
npm run lint
npm test
npm run build
# Нужны запущенный frontend и установленный Google Chrome:
npm run test:account
npm run test:viewer
```

Account-тесты покрывают DTO, GET/JWT, нулевой остаток, безлимит, PAST_DUE, отмену в конце
периода, частичные ошибки, устаревшие данные, таймаут, смену аккаунта, ротацию JWT,
обновление при фокусе и границу периода. Browser smoke проверяет весь App:
принятую и отклонённую загрузку, обновление по завершению задачи, меню, темы,
языки, мобильную ширину и возврат к книге.

Браузерные проверки используют изолированные ответы API и не создают задач на настоящем
backend. Их тестовый лимит 10 — фикстура, не реальный лимит сервиса.
Отдельно проверены реальные GET endpoints через Vite-прокси на тестовом аккаунте:
оба вернули 200; созданная для проверки сессия завершена с 204.
