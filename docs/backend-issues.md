# Что исправить или доработать на бэке

Найдено при подключении фронтенда. Здесь только описание проблемы и где она
видна; как исправлять — решает владелец бэка. Проверено на `origin/master`
бэка (`183c7cb`, 2026-11-19) и на локальном контейнере, если не сказано иное.

Статусы: **открыто** — проблема есть; **решено** — исправлено на бэке (с коммитом).

## Смена почты

### 1. Нельзя узнать, что смена почты ждёт подтверждения — открыто

`POST /api/account/email-change` отвечает 202, но запроса, который вернул бы
незавершённую смену (новый адрес, срок ссылки), нет. После перезагрузки страницы
профиль не может показать «ждём подтверждения на new@…»: пользователь не видит,
что смена запущена, и не помнит, на какой адрес ушло письмо. Отменить её из
профиля тоже нельзя — только по ссылке из письма на старый адрес.

### 2. Занятый адрес неотличим от свободного, и письма не приходит никому — открыто

Если новый адрес принадлежит другому аккаунту, `request` отвечает тем же 202
(`EmailChangeTransactionService.request`, `takenByAnother → return`), но письма
не отправляются ни на новый адрес, ни на текущий. Ответ одинаковый намеренно
(защита от перебора аккаунтов), но в итоге человек ждёт письмо, которое не
придёт, и ничто ему об этом не скажет — даже письмо на текущий адрес о запросе.

### 3. После подтверждения ссылка «это был не я» перестаёт работать — открыто

Письмо на старый адрес говорит: «Если это были не вы, отмените смену по ссылке».
Но `confirm` гасит все открытые ссылки пользователя
(`tokens.consumeAllOpenForUser`), включая эту. Если смену подтвердил тот, кто
знает пароль, владелец старого адреса получает письмо со ссылкой, которая уже
отвечает `400 INVALID_ACTION_LINK`, и вернуть аккаунт через письмо не может.
Текст письма при этом обещает обратное.

### 4. Повторное открытие ссылки неотличимо от испорченной — открыто

Повторный `POST /api/account/email-change/confirm` с уже использованным токеном
отвечает `400 INVALID_ACTION_LINK` — так же, как просроченная или чужая ссылка.
Если человек открыл ссылку второй раз (или первый ответ потерялся в сети), фронт
может сказать только «ссылка недействительна», хотя почта уже сменилась. То же
для `cancel`.

## Ошибки API

### 5. Несуществующий адрес API отвечает 500 — открыто

`GET /api/no-such-route` → `500 INTERNAL_ERROR`, и в лог пишется ERROR
«Непредвиденная ошибка». В `GlobalExceptionHandler` нет обработки
`NoResourceFoundException`, она попадает в общий `@ExceptionHandler(Exception.class)`.
Для клиента опечатка в пути и настоящий сбой сервера выглядят одинаково, а
мониторинг считает ошибкой сервера каждую такую попытку.

## Контракт

### 6. Разный стиль имён полей в JSON — открыто

Большая часть API — `snake_case` (`/profile`, `/account/sessions`,
`/account/usage`, `/account/desktop`). Но в аккаунте и входе — `camelCase`:

- запросы: `currentPassword`, `newPassword`, `newEmail`, `recoveryCode`;
- ответы: `recoveryCodesLeft`, `recoveryCodes`, `secondFactorRequired`,
  `expiresIn`, `accessToken`, `otpauthUri`.

Одно и то же поле пишется по-разному: пароль для подтверждения — `currentPassword`
в `/account/password` и `/account/second-factor/*`, но `current_password` в
`/account/desktop/license-key`. Фронту приходится помнить стиль для каждого
запроса. Поле с «не тем» именем бэк пропускает молча, и ответ — 400 «поле не
заполнено», хотя поле отправлено.

### 7. Имя продукта в приложении-аутентификаторе — открыто

`otpauthUri` подписан `TranslateLab` (`app.second-factor.issuer`), письма — тоже
TranslateLab, а интерфейс называется Parallel. В приложении-аутентификаторе
человек увидит название, которого нет на сайте. Нужно решить, какое имя
показывать пользователю.

## Локальное окружение

Не ошибки кода, но из-за этого часть сценариев нельзя проверить вживую.

- **Почта не отправляется** (`ACCOUNT_EMAIL_DELIVERY_ENABLED=false`, перехватчика
  почты в `compose` нет). Подтверждение почты, сброс пароля и смену почты нельзя
  пройти до конца: письмо со ссылкой никуда не уходит.
- **Ссылки из писем ведут на `http://localhost:3000`** (`FRONTEND_BASE_URL`), а
  фронт в разработке открыт на `5173`.
- **Двухэтапная проверка выключена**: `SECOND_FACTOR_ENCRYPTION_KEY` пуст, и
  `POST /account/second-factor/setup` отвечает `503 SECOND_FACTOR_UNAVAILABLE`.
- **Админка недоступна**: `/api/admin/*` требует включённую двухэтапную проверку
  (`403 SECOND_FACTOR_REQUIRED`), а включить её локально нельзя (пункт выше).
- **Контейнер собран не из `origin/master`**: в нём нет раздела Desktop
  (`/api/account/desktop` отвечает 500 — см. п. 5).
