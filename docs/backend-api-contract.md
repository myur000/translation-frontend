# Backend API contract

Контракт зафиксирован по Java-коду backend. Backend в рамках frontend-задачи
не изменяется.

## Адреса

- Локальный backend: `http://localhost:8080`.
- Frontend dev server: `http://localhost:3000`.
- Browser API base URL: `/api`.
- Vite перенаправляет `/api/*` в `http://localhost:8080/api/*`.

Такой режим выбран намеренно: CORS в backend по умолчанию выключен. Для прямых
запросов браузера на `http://localhost:8080` backend пришлось бы запускать с
`CORS_ENABLED=true` и
`CORS_ALLOWED_ORIGINS=http://localhost:3000`.

## Аутентификация и JWT

Защищённые запросы используют заголовок
`Authorization: Bearer <access-token>`. Access token действует 15 минут
по умолчанию. Backend с контрактом от 2026-10-07 поддерживает refresh-сессию
на 7 дней: HttpOnly cookie `translatelab_refresh`, Path `/api/auth`.
JWT хранится в памяти frontend, cookie управляется только браузером.

После подтверждения email старый JWT также становится недействительным: claim
`email_verified` больше не совпадает с состоянием аккаунта. Refresh выдаёт JWT
с актуальным состоянием; текущий экран подтверждения предлагает повторный вход.

JWT подписан `HS256`. Backend проверяет подпись, `issuer`, `audience`, `kid`,
срок действия и `auth_version`. Payload содержит `sub`, `email`,
`email_verified`, `auth_version`, `sid` (новые сессии), `iat`, `exp`, `iss` и `aud`. Клиент может
использовать claims только для отображения; окончательное решение о доступе
всегда принимает backend.

Загрузка документов и начало покупки требуют JWT подтверждённого аккаунта.

Login/refresh/logout/logout-all отправляются с `credentials: "include"`.
Refresh и logout требуют `X-Refresh-Request: true`; Bearer для них не нужен.
Frontend обновляет JWT за минуту до истечения и после 401 защищённого запроса,
повторяя исходный запрос максимум один раз. Вкладки сериализуют cookie-операции
через Web Locks и делятся результатом через BroadcastChannel (JWT только в памяти).
401 refresh завершает вход; 403, 429, 5xx и сеть не считаются истечением сессии.
После неопределённого результата автоматические повторы заблокированы до нового
входа; несекретный маркер сохраняет это правило даже после перезагрузки страницы.
Обычный выход теперь отзывает текущую сессию на backend, а не только очищает UI.

### Upload contract

`multipart/form-data` содержит `file`, `source_lang`, `target_lang`. Разрешены
`pdf`, `doc`, `docx`, максимальный размер по умолчанию — 20 MB. Коды языков —
NLLB-200 (`eng_Latn`, `rus_Cyrl`, …) из `GET /api/languages`; старые коды
`en`/`ru`/`de` backend отклоняет с `400`. Исходный и целевой языки должны
различаться.

### Языки

Каталог — 202 языка, `[{"code": "rus_Cyrl", "name": "Русский"}]`, отсортирован
по русскому названию. Frontend загружает его один раз за сессию страницы, при
первом открытии выбора языка (`src/languages/languageCatalog.ts`). Подписи:
в русском интерфейсе — `name` из каталога, в английском — `Intl.DisplayNames`
(для языков с несколькими письменностями добавляется письменность), иначе
русское название или сам код. «Часто используемые» языки доступны, даже если
каталог не загрузился.

У документов, созданных до перехода на NLLB, в истории остались коды
`en`/`ru`/`de`: они показываются по названию языка, а при повторном переводе
выбор подставляет соответствующий NLLB-код. Атрибут `lang` панелей получает
BCP 47 (`eng_Latn` → `en-Latn`).

Отдельного endpoint запуска перевода нет. Успешная загрузка сразу создаёт
асинхронное задание и возвращает `job_id`.

### Скачивание результата

`GET /api/documents/{jobId}/download` требует Bearer JWT владельца задачи.
Успешный ответ — бинарный файл с Content-Type и Content-Disposition
(`translation-{jobId}.{format}`). Frontend использует имя из заголовка;
если заголовок отсутствует, берёт имя оригинала с суффиксом языка перевода.
Файл скачивается через временный Blob URL, который освобождается после запуска
сохранения. Токен не помещается в ссылку или имя файла.

Кнопка активна только для задачи DONE с job_id. Во время запроса она показывает
«Скачиваем…»; повторные клики заблокированы. Смена книги или выход отменяет запрос.
Скачивание использует общую обработку обновления JWT и один повтор после 401.
Ошибки: 404 — задача не найдена/не принадлежит пользователю, 409 — результат
не готов, 410 — результат удалён по сроку хранения. Также обрабатываются
403, 429 с Retry-After, сетевые ошибки и недоступность сервера.

## Статусы перевода

- `PENDING` — принято и ожидает ML worker.
- `PROCESSING` — перевод выполняется.
- `DONE` — результат готов к скачиванию.
- `FAILED` — перевод завершился ошибкой.
- `CANCELED` — перевод отменён владельцем (с 2026-11-09). Финальный, как `DONE`
  и `FAILED`: скачать нечего, документ можно удалить или перевести снова.

Единственный текущий публичный `error_code`: `TRANSLATION_FAILED`.

### Отмена перевода

`POST /documents/{jobId}/cancel` без тела, только для `PENDING`/`PROCESSING`
(`src/api/documents.ts`, `cancelDocumentTranslation`). Ответ устроен как статус.
Поле `quota_refund` есть в статусе, истории и ответе отмены; у неотменённых
задач оно `null`:

| `quota_refund` | Смысл | Что показывает frontend |
| --- | --- | --- |
| `REFUNDED` | перевод не начинался, страницы вернули | «Списанные страницы вернулись на счёт», «списано N стр.» скрыто |
| `PENDING` | ждём ответа сервиса перевода (секунды, не дольше суток) | «Возврат страниц уточняется», задача остаётся в опросе и SSE |
| `NONE` | перевод уже шёл, страницы не возвращаются | «Он уже начался, поэтому списанные страницы не вернутся» |

- Отменить можно из нижней панели (кнопка «Отменить» рядом с прогрессом) и из
  меню «⋯» документа в шапке и боковой панели. Диалог подтверждения
  (`CancelTranslationDialog`) для `PROCESSING` предупреждает, что страницы не
  вернутся; кнопка закрытия — «Продолжить перевод», а не двусмысленная «Отмена».
- `409 DOCUMENT_ALREADY_FINISHED` — перевод успел завершиться: диалог объясняет
  это, а frontend сразу перечитывает статус, чтобы документ не остался
  «переводящимся». `404` — документ удалён в другой вкладке. Повторная отмена
  безопасна (`200`).
- Отменённая задача повторяется кнопкой «Повторить» так же, как неудачная:
  локальным файлом или по оригиналу на сервере (`410`, если он удалён по сроку).
- Расход (`/account/usage`) перечитывается на каждом финальном состоянии,
  включая уточнение возврата `PENDING` → `REFUNDED`.

### Поток статусов (SSE)

Пока есть незавершённые документы (или отменённые с `quota_refund: PENDING`),
рабочая область держит один поток
`GET /api/documents/events` (`src/hooks/useDocumentEvents.ts`). `EventSource`
не умеет передавать `Authorization`, поэтому поток открывается через API-клиент
(`requestStream`: подготовка токена и один повтор после 401) и разбирается
парсером `src/api/sse.ts`.

- `job` — сразу обновить статус и прогресс; на `DONE`/`FAILED`/`CANCELED`
  прочитать полный статус: в событии нет текста ошибки и `quota_refund`.
  Повторное событие `CANCELED` приходит, когда уточнился возврат страниц.
- `ready`, `resync` — перечитать статусы незавершённых документов.
- Поток, закрытый сервером (истёк токен, периодическая ротация), открывается
  снова; сетевые ошибки — с экспоненциальной задержкой до 30 секунд.
- `404` (потоки выключены) и `429` (больше 5 потоков на аккаунт) — поток
  отключается до перезагрузки страницы.

Опрос `GET /status` остаётся страховкой: раз в 30 секунд при живом потоке и раз
в 2,5 секунды без него. Логика «статус не меняется 2 минуты» не изменилась.

## Документы: ссылка, удаление, другой язык, оценка

- Маршрут `/documents/:jobId` — страница документа; на неё ведёт письмо о
  готовности перевода. Задачи с первой страницы истории открываются сразу;
  более старые подтверждаются запросом статуса и ищутся на следующих страницах
  истории. `404` — экран «Документ не найден». Выбор документа и успешная
  загрузка переводят URL на задачу.
- `file_name` из истории и статуса показывается вместо локального имени; у
  старых задач (`null`) остаётся имя из `sessionStorage`.
- Меню «⋯» в панели инструментов: «Перевести на другой язык» и «Удалить
  документ». Перевод на другой язык берёт оригинал, хранящийся на backend,
  поэтому файл не нужен; каждый отличающийся запрос получает свой
  `Idempotency-Key`, повтор того же запроса — тот же ключ. Неудачный перевод
  повторяется так же, без выбора оригинала. `410` — оригинал удалён по сроку.
- Удаление: подтверждение, `DELETE`; `409 DOCUMENT_STILL_PROCESSING` — документ
  ещё переводится (удалить можно после завершения или отмены, пункт меню
  недоступен с подсказкой об этом); `404` считается уже удалённым. Черновик
  удаляется только локально.
- Стоимость черновика (`POST /documents/estimate`) показывается под именем
  файла, при нехватке квоты — предупреждение. Для неподтверждённого email
  оценки нет (`403`), это не ошибка.
- Глоссарий: галочка «Глоссарий · N» видна, только если для пары языков есть
  термины; `use_glossary=true` уходит с загрузкой и переводом на другой язык;
  `glossary_term_count` и `billed_units` показываются под именем файла.
- Оценка перевода: звёзды 1–5 в заголовке панели «Перевод» у готовых
  документов и необязательный комментарий. Повторная оценка отправляет и
  текущий комментарий: backend заменяет их вместе.

## Регистрация и заблокированный аккаунт

Регистрация всегда отвечает `202` без тела, в том числе для занятого email:
backend не раскрывает, существует ли аккаунт, а владельцу адреса уходит письмо
подтверждения или сброса пароля. Экран успеха поэтому просит проверить почту
и не утверждает, что аккаунт создан.

Администратор может заблокировать аккаунт. Тогда вход с верным паролем
возвращает `403`, и форма входа показывает «Аккаунт заблокирован», а не
«неверный пароль». Уже открытые сессии закрываются: следующий запрос и refresh
получают `401`, frontend ведёт себя как после выхода.

## Ошибки

Все REST-ошибки имеют один wire-format:

```json
{
  "timestamp": "2026-10-02T10:15:30Z",
  "status": 400,
  "code": "VALIDATION_FAILED",
  "message": "Ошибка валидации запроса",
  "path": "/api/auth/register",
  "fieldErrors": {
    "email": "must be a well-formed email address"
  },
  "correlation_id": "request-correlation-id"
}
```

Frontend должен учитывать `400`, `401`, `403`, `404`, `409`, `410`, `413`,
`415`, `429`, `500`, `503`. Для `429` и части `503` backend возвращает
`Retry-After`; correlation ID также доступен в заголовке `X-Correlation-ID`.

**Машинный код `code`** (с 2026-11-09, список — README backend, «Коды ошибок»).
Ошибки с одинаковым статусом различаются по нему, а не по тексту `message`:
`ApiClientError.code` и `hasApiErrorCode(error, 'USAGE_LIMIT_EXCEEDED')`
(`src/api/client.ts`). Известные frontend коды перечислены в
`KnownApiErrorCode` (`src/api/contracts/common.ts`); неизвестный код
обрабатывается по HTTP-статусу. Поле необязательное: ответ без него (например,
от прокси) разбирается как раньше, `code` равен `null`.

Где frontend уже различает по коду:

| Код | Статус | Где |
| --- | --- | --- |
| `USAGE_LIMIT_EXCEEDED` | 429 | загрузка и перевод на другой язык: «квота исчерпана», а не «слишком много запросов» (`RATE_LIMIT_EXCEEDED`). Раньше различалось по тексту сообщения |
| `DOCUMENT_STILL_PROCESSING` | 409 | диалог удаления |
| `DOCUMENT_ALREADY_FINISHED` | 409 | диалог отмены перевода |

**Известное ограничение (гонка оценки и загрузки).** Backend держит не больше
одного одновременного запроса на загрузку от аккаунта (`FileOperationAdmission`)
и сразу отвечает `429 RATE_LIMIT_EXCEEDED`, `Retry-After: 1`. Оценка стоимости
(`/estimate`) занимает тот же слот, поэтому «Перевести», нажатое, пока оценка
черновика ещё идёт, получает «Слишком много загрузок». Найдено при живой
проверке 2026-11-14; исправление на стороне frontend — отдельной задачей.

## Заметки (этап 1: раздел «Заметки»)

Раздел `/notes`, `/notes/new`, `/notes/:id`; контракт — `src/api/contracts/notes.ts`,
запросы — `src/api/notes.ts`. Граф и цитаты из книг подключаются на следующих этапах.

- **Фильтры в адресе.** `?q=` (поиск) и `?tag=` — единственный источник фильтра
  списка: их понимают ссылки на теги в тексте, «Назад» и боковая панель.
- **Теги.** Отдельного списка тегов backend не отдаёт; он строится из графа
  (узлы `tag:…` и рёбра `tagged`). Граф запрашивается один раз на приложение —
  `GET /api/notes/graph?types=document,tag,missing` в `NotesProvider`: из него
  же дерево панели заметок и книги на главной раздела.
- **Порядок списка.** Без `q` backend сортирует по `updated_at DESC, id`
  (`NoteIndexStore`), поэтому первые заметки — последние изменённые: на этом
  стоит «Продолжить» на главной и «Недавние» в панели. С `q` первым идёт
  `ts_rank`.
- **Синтаксис** `[[…]]` и `#тег` frontend разбирает по тем же правилам, что
  `NoteMarkup` backend (`src/notes/noteSyntax.ts`): тег не начинается после буквы,
  цифры, `_ # / & [`; из одних цифр — не тег; в коде ссылки и теги не ищутся.
- **Markdown** (`markdown-it`, `html: false`) + DOMPurify: ссылки только
  `http(s)`, внутренние `/…` и `#`; картинки показываются ссылкой (не грузятся
  сами). Внешние ссылки — `target="_blank" rel="noopener noreferrer"`.
- **409 без машинного кода.** «Изменили в другом окне», «название занято» и
  «лимит» различаются только текстом. После 409 на `PUT` frontend перечитывает
  заметку: версия выросла — показывает конфликт («Загрузить актуальную» /
  «Сохранить мою» с новой `version`); не выросла — текст ошибки сервера.
  **Запрос к backend:** добавить код ошибки в `ApiError` для этих случаев —
  выполнено 2026-11-09 (`NOTE_CONFLICT`, `INVALID_NOTE`); перевод заметок на
  коды — отдельной задачей.
- **403** на запись — сообщение о подтверждении email (общий обработчик доступа
  для записи заметок отключён).
- **Черновики** несохранённой правки хранятся в памяти вкладки (не в
  `sessionStorage`) и восстанавливаются при возврате к заметке; закрытие вкладки
  с правкой — `beforeunload`.

## Конспект книги: заметка о документе без цитаты (T-67)

Backend с 2026-11-14 привязывает заметку к документу целиком.

- **Контракт.** `NoteCreateRequest.job_ids` — привязка при создании (вместе с
  `quote` тоже можно); `POST /api/notes/{id}/documents {job_id}` → `200
  NoteResponse` (повторная привязка ничего не меняет); `DELETE
  /api/notes/{id}/documents/{jobId}` → `204`, `404`, если связи нет. У
  `NoteResponse` — `documents[]` (`job_id`, `document_name`,
  `document_available`, `linked_at`; у удалённой книги имя `null`, но `job_id`
  есть, чтобы связь можно было снять), у `NoteSummary` — `linked_job_ids`. В
  графе — ребро `about` (заметка → документ). `GET /api/notes?job_id=` отдаёт
  заметки с цитатами **и** привязанные, каждую один раз. Статус документа не
  важен: конспект можно начать, пока книга переводится. Больше 50 документов —
  `400 NOTE_DOCUMENT_LIMIT_REACHED` (показывается текст сервера), чужой или
  удалённый — `404 DOCUMENT_NOT_FOUND` («Книга удалена или недоступна», а не
  «Заметка не найдена»). Поля `documents` и `linked_job_ids` в типах
  необязательные: ответы до T-67 их не содержат.
- **В книге.** Меню «+» нижней панели: «Начать конспект книги» (черновик с
  названием «Конспект — <название книги>» и `job_ids: [jobId]`) или, если
  конспект есть, «Конспект книги» (открыть). На полях конспект — карточка
  «Конспект книги» у верха страницы, над заметками к абзацам; в колонке —
  сверху списка со значком §. Конспекты читаются тем же загрузчиком, что и
  цитаты (`loadBookNotes`): заметки книги с цитатами или привязкой.
- **В разделе «Заметки».** В дереве по книгам конспект первым в группе своей
  книги, со значком тетради (раньше такая заметка попала бы в «Без книги»).
  На странице заметки — раздел «О книгах»: привязанные книги со ссылками и
  «×» (отвязать), ниже выбор своей книги и «Привязать».

## Заметки рядом с книгой и цитаты (этап 2)

Панель справа в рабочей области (`WorkspaceNotesPanel`, грузится лениво):
заметки с цитатами из этой книги (`GET /api/notes?job_id=`), все заметки с
поиском, просмотр и правка заметки без ухода со страницы.

- **Цитата из выделения.** Над выделенным текстом колонки — кнопка «В заметку».
  Backend хранит номер абзаца, а не смещения: frontend загружает
  `GET /api/documents/{jobId}/text` (обе стороны, кэш на сеанс) и находит абзац
  по тексту (`src/notes/quoteLocator.ts`): текстовый вид оригинала отдаёт номер
  напрямую (`data-paragraph-index`), в DOCX/PDF — поиск по тексту с уточнением
  по блоку, где началось выделение; выделение через несколько абзацев
  привязывается к первому. `paired_text` — абзац другой стороны, только если
  `aligned: true`. Цитата > 2000 символов сокращается.
- **`/text` делит файловый слот со скачиванием** — при `429` запрос повторяется
  по `Retry-After` (до двух раз).
- **Исходник удалён** (`source_available: false`) — цитировать можно только
  перевод; пользователь видит объяснение.
- **«Показать в книге»** прокручивает колонку к абзацу и подсвечивает его.
- **Удаление книги**: диалог сообщает, в скольких заметках останутся цитаты
  (`GET /api/notes?job_id=&size=1` → `total_elements`).

## Текст оригинала (`/text`) и оставшийся разрыв с UI

Исходный файл скачать нельзя. Пока файл оригинала есть в памяти вкладки
(сразу после загрузки или выбранный вручную), frontend показывает его с
оформлением. После перезагрузки оригинал берётся из
`GET /api/documents/{jobId}/text`: абзацы собираются со всех страниц ответа
(`size=500`, не больше 20 запросов) и выводятся простым текстом
(`white-space: pre-line`, без HTML). Перевод по-прежнему скачивается через
download и разбирается в браузере с оформлением.

- `/text` и download делят **один файловый слот аккаунта**: параллельный
  второй запрос получает `429`. Поэтому frontend запрашивает текст только
  после того, как скачивание перевода завершилось.
- `source_available: false` — исходник удалён по сроку хранения (сейчас через
  сутки после перевода): показывается сообщение и выбор файла на устройстве.
- Ошибка `/text` не блокирует просмотр: доступны «Повторить» и выбор файла.
- `truncated: true` — под текстом пояснение, что конец не показан.
- Ограничения: у текста нет оформления (заголовки, списки, таблицы выглядят
  как абзацы). DOC и PDF приходят тем же списком абзацев.

Реализованный поток и ограничения форматов: [просмотр документов](real-document-viewer.md).

Backend формирует email-ссылки на `/verify-email?token=...` и
`/reset-password?token=...`. Эти frontend-маршруты и API-запросы реализованы.
Доставка писем зависит от SMTP-настроек backend.
