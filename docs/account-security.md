# Вход и безопасность аккаунта

Профиль (`/profile`) разбит на разделы: «Профиль» (фото и имя, см.
[редактирование профиля](profile-editing.md)), «Вход и безопасность» и
«Сеансы». Слева — навигация по разделам, на телефоне она переносится строкой
над карточками. Страница грузится отдельным куском кода (`lazy` в `App.tsx`):
основной бандл не растёт.

Проблемы бэка, найденные по ходу, — в [backend-issues.md](backend-issues.md).

## Что где

| Файл | Что делает |
| --- | --- |
| `api/accountSecurity.ts`, `api/contracts/accountSecurity.ts` | Запросы и типы; ответы проверяются при разборе |
| `account/securityQueries.ts` | React Query: сеансы и статус второго фактора, ключи `['account', владелец, …]` |
| `account/securityErrors.ts` | Коды ошибок бэка → текст и поле, которое подсветить; проверка длины пароля |
| `auth/sessionController.ts` | `login` с ответом 202, `completeSecondFactor`, `replaceSession` |
| `auth/linkToken.ts` | Токен из ссылки письма |
| `components/profile/security/*` | Строки «Почта», «Пароль», «Двухэтапная проверка», окно резервных кодов |
| `components/profile/SessionsSection.tsx` | Список сеансов и «Выйти на всех устройствах» |
| `components/auth/SecondFactorStep.tsx` | Второй шаг входа |
| `pages/EmailChangeLinkPage.tsx` | `/confirm-email-change` и `/cancel-email-change` |

Формы раскрываются прямо в строке раздела. Отдельное окно — только для
резервных кодов: они показываются один раз.

## Ссылки из писем

С 2026-10-31 бэк кладёт токен во фрагмент: `/verify-email#token=…`. Фрагмент не
уходит на сервер и не попадает в логи и Referer. Фронт читал `?token=`, поэтому
страницы подтверждения почты и сброса пароля по новым письмам показывали «нет
токена». `readLinkToken` берёт фрагмент, а для старых писем — query.

Смена почты подтверждается **кнопкой**, а не запросом при открытии страницы.
Почтовые сканеры сами открывают ссылки из писем. Ссылка отмены при этом
завершила бы все сеансы человека без его ведома.

| Ответ | Что видит человек |
| --- | --- |
| `204` confirm | «Почта изменена», локальная сессия завершается (бэк завершил все) |
| `204` cancel | «Смена отменена», совет сменить пароль |
| `400 INVALID_ACTION_LINK` | Ссылка устарела или использована; если почта уже сменилась — войти с новым адресом |
| `409 EMAIL_ALREADY_USED` | Адрес заняли, пока письмо шло; почта не изменена |

## Вход с двухэтапной проверкой

`POST /auth/login` отвечает 202 `{secondFactorRequired, challenge, expiresIn}`,
если у аккаунта включена проверка. Раньше фронт считал любой ответ сессией, и
такой аккаунт не мог войти. Теперь `login` возвращает `LoginResult`:
`signed-in` или `second-factor`. Страница входа показывает второй шаг: код из
приложения (6 цифр) или резервный код. Код уходит в
`POST /auth/login/second-factor` под той же блокировкой cookie, что и вход.

- `400 INVALID_SECOND_FACTOR_CODE` — «Неверный код», можно повторить.
- `401 LOGIN_CHALLENGE_EXPIRED` — возврат к паролю с объяснением, пароль очищен.
- `429` — сколько ждать.

## Смена пароля

Бэк завершает все сеансы и в ответе выдаёт этому устройству новую сессию
(`LoginResponse` и новая refresh-cookie). `replaceSession` выполняет запрос под
межвкладочной блокировкой cookie и раздаёт новую сессию соседним вкладкам. Без
блокировки соседняя вкладка могла продлить сессию старой cookie, получить 401 и
разлогинить все вкладки. Проверено вживую: после смены пароля обе вкладки
остались в аккаунте, список сеансов сократился до одного.

На фронте проверяется длина: 8–72 символа, причём 72 считаются в байтах UTF-8,
как у bcrypt на бэке. Слабый пароль (`WEAK_PASSWORD`) бэк объясняет сам, и
показывается его текст. Неверный текущий пароль подсвечивает своё поле.

## Смена почты

`POST /account/email-change` с новым адресом и паролем → 202. Почта не
меняется, пока не открыта ссылка из письма. Узнать о незавершённой смене бэк не
позволяет, поэтому сообщение «письмо отправлено» видно только сразу после
отправки. Текст честно говорит «если адрес свободен»: на занятый адрес бэк
отвечает тем же 202, но писем не шлёт.

## Двухэтапная проверка

1. Пароль → `setup` → секрет и `otpauth://`-ссылка.
2. Секрет показывается группами по четыре символа для ручного ввода. Ссылка на
   телефоне открывает приложение-аутентификатор.
3. Код → `enable` → резервные коды. Остальные сеансы бэк завершает, список
   сеансов перечитывается.
4. Окно с кодами: «Скопировать», «Скачать .txt», «Я сохранил коды». Esc и
   щелчок мимо окно не закрывают, иначе коды потерялись бы.

Новые коды требуют пароль и код из приложения: резервным кодом новые не
получить. Выключение — пароль и код из приложения или резервный код. Когда
кодов осталось два и меньше, показывается предупреждение.

QR-кода пока нет: для него нужна библиотека генерации, а добавить зависимость
не согласовано. Секрет и ссылка работают без QR.

Локально `setup` отвечает `503 SECOND_FACTOR_UNAVAILABLE` (не задан ключ
шифрования) — показывается «сейчас недоступна». Полный путь подключения
проверен тестами на моках.

## Сеансы

`GET /account/sessions`: текущий сеанс первым, остальные — от недавних к
давним. Если устройство не распознано, оно называется «Неизвестное устройство».
Время показывается как «сегодня в 14:05», «вчера в 21:40» или «12 ноября».
Список перечитывается при возврате на вкладку: его меняют и другие устройства.

У текущего сеанса кнопки «Завершить» нет: для этого есть выход. Сеанс,
который уже закончился сам (`404 SESSION_NOT_FOUND`), просто убирается из
списка. «Выйти на всех устройствах» перенесён в этот раздел без изменений.
